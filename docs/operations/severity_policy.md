# Severity 운영 정책

본 문서는 베타테스트 이슈의 Severity 라벨 운영 기준을 정의합니다.
PRD v4.1 §4.1.2가 위임한 운영 세부 정책의 정본(SSoT)입니다.

## 라벨 체계

| 라벨 | 의미 | 응답 SLA | LLM 분석 | 일일 보고 노출 |
|------|------|---------|---------|--------------|
| P1   | Critical — 서비스 중단·데이터 손실·보안 사고 | 1영업일 내 분석 PR 머지 | ✅ 필수 | ✅ 상단 강조 |
| P2   | High — 핵심 기능 오류·다수 사용자 영향 | 3영업일 내 분석 PR 머지 | ✅ 필수 | ✅ 포함 |
| P3   | Medium — 일부 기능 오류·우회 가능 | 1주 내 검토 | ✅ 권장 | ✅ 통계만 |
| P4   | Low — Nice-to-have·UX 개선·문서 오류 | 백로그 적재 | ❌ 미실행 | 통계만 |

## P4 운영 가이드

P4는 다음 케이스를 포괄합니다:
- **개선 제안 성격**: "이런 기능이 있으면 좋겠다"
- **UX 사소한 문제**: 텍스트 줄바꿈, 색상 일관성 등
- **문서·메시지 개선**: 오타, 표현 모호함
- **장기 개선 백로그**: 즉시 처리는 불필요하나 기록 가치 있음

### LLM 분석 제외 정책 (PRD B-3, B-8 비용 제한 반영)

P4는 **LLM 분석을 자동 실행하지 않습니다.** 이유:
- LLM 호출당 토큰 비용이 발생함 (PRD B-8)
- P4는 즉시성이 낮아 자동 분석의 ROI가 낮음
- 필요 시 `/reanalyze` 코멘트로 수동 트리거 가능 (PRD B-9)

### 분석 PR 생성 제외 정책 (PRD B-4 반영)

P4는 GitHub Issue로만 등록되며, 분석 PR(`analysis/issue-{N}` 브랜치)은 
자동 생성하지 않습니다. 필요 시 개발자가 직접 일반 PR을 생성합니다.

## 운영자의 라벨 재분류

LLM 또는 폼 제출자가 부여한 Severity는 운영자가 GitHub Issue에서 
직접 변경할 수 있습니다. 재분류 시 Raw Issues 시트의 해당 컬럼이 
자동 갱신됩니다 (PRD C-3 PR 상태 자동 갱신 흐름과 별개).
